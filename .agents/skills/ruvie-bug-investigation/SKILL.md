# Диагностика дефекта Ruvie

Цель — доказать root cause, исправить минимальную причину и защитить поведение regression-тестом. Не превращай диагностику в несвязанный рефакторинг.

## Сначала установи факты

1. Прочитай применимые `AGENTS.md` и нужный сценарий в `docs/full-product-documentation.md`.
2. Зафиксируй ожидаемое и фактическое поведение.
3. Найди минимальное воспроизведение: тест, browser flow, API request или последовательность состояний.
4. Проследи данные от UI до Route Handler, service/operation, Prisma и внешней интеграции.
5. Проверь соседние тесты, логи и error codes. Не считай корреляцию причиной.

Для auth, credits, payments и generations отдельно проверь:

- повтор запроса и потерю ответа;
- idempotency key;
- конкурентные операции;
- query cache и reconciliation;
- terminal state;
- refund/cleanup;
- ownership и статус профиля.

Для canvas и browser state проверь:

- mount/unmount;
- race между autosave, export и network;
- IndexedDB/localStorage fallback;
- stale server version;
- pointer/keyboard события;
- размеры и coordinate space.

## Исправление

- Если пользователь просил только диагностику, не изменяй файлы.
- Если просил исправить, сначала добавь тест или воспроизведение, падающее по подтверждённой причине.
- Исправь первопричину на самом узком корректном уровне.
- Не скрывай ошибку retry, задержкой, ослаблением assertion или подавлением exception.
- Сохрани существующие бизнес-инварианты и обратную совместимость, если изменение контракта не было частью задачи.
- Обнови документацию, если фактическое продуктовое поведение изменилось.

## Проверка

Запусти regression-тест, соседний suite и статические проверки затронутого приложения. Для race/concurrency используй детерминированный тест, а для визуального/browser дефекта — реальный browser flow.

В финале отдели:

- симптом;
- доказанный root cause;
- исправление;
- regression protection;
- выполненные проверки;
- остаточный риск.
