# Ruvie — полная документация продукта и бизнес-флоу

> Актуально для состояния репозитория на 17 сентября 2026 года.
> Документ описывает реализованное поведение пользовательского приложения, отдельной административной панели, backend API, бизнес-правила, состояния и основные эксплуатационные ограничения.

## 1. О продукте

Ruvie — веб-сервис AI-визуализации интерьера по фотографии помещения. Пользователь загружает фотографию комнаты, размечает зоны изменений прямо на изображении, добавляет референсы, выбирает назначение комнаты, стиль и формат, описывает желаемый результат и запускает генерацию. Полученный вариант можно открыть, скачать и использовать как основу для точечной доработки.

Ключевой продуктовый принцип: исходная фотография, все варианты и дочерние доработки находятся на одном бесконечном холсте и образуют неизменяемую историю проекта.

Система должна стремиться сохранять:

- исходный ракурс камеры;
- геометрию и пропорции помещения;
- расположение стен, окон и дверей;
- основные архитектурные элементы;
- связь между исходником, результатом и последующими доработками.

## 2. Состав системы

Проект состоит из трёх логических приложений:

1. Пользовательский frontend — Next.js App Router, React 19, Tailwind CSS, shadcn/Radix.
2. Backend — Next.js Route Handlers, Prisma, PostgreSQL, Supabase Auth/Storage, Google Vertex AI или fake provider.
3. Отдельная административная панель — Vite, React Router, Mantine и TanStack Query.

Основные каталоги:

```text
src/app       — маршруты Next.js и HTTP Route Handlers
src/client    — пользовательский frontend
src/server    — backend и бизнес-операции
admin/src     — отдельный frontend админ-панели
prisma        — схема базы и миграции
```

## 3. Роли и права доступа

### 3.1. Неавторизованный посетитель

Может:

- открыть лендинг;
- изучить примеры, сценарии, FAQ и публичные пакеты кредитов;
- открыть публичную оферту и политику конфиденциальности;
- перейти к Google OAuth после принятия документов.

Не может:

- создавать и просматривать проекты;
- загружать файлы;
- получать приватные signed URL;
- создавать генерации;
- просматривать профиль, баланс и финансовые операции.

### 3.2. Пользователь

Профиль с ролью `USER` или `ADMIN` и статусом `ACTIVE` может работать в основном приложении только со своими данными:

- создавать проекты;
- загружать исходную фотографию;
- размечать изображение;
- добавлять и упорядочивать референсы;
- запускать, отменять и повторять генерации;
- создавать доработки от успешных вариантов;
- просматривать и скачивать результаты;
- просматривать каталог своих завершённых проектов;
- редактировать отображаемое имя;
- просматривать баланс и кредитные операции;
- покупать пакеты, если платежный provider включён.

Профили `BLOCKED` и `DELETED` не допускаются к защищённым бизнес-операциям.

### 3.3. Администратор

Администратор — активный профиль с ролью `ADMIN`, прошедший отдельную авторизацию административной панели. Он может:

- видеть сводную статистику;
- искать пользователей и открывать их карточки;
- изменять роль и статус пользователей;
- вручную начислять и списывать кредиты с обязательной причиной;
- просматривать генерации, их входы, историю, стоимость, ошибки и медиа;
- отменять допустимые активные генерации;
- управлять типами комнат;
- просматривать платежные заказы и все кредитные операции;
- создавать, редактировать, отключать и удалять пакеты кредитов.

Администратор не может через API заблокировать, удалить или лишить роли `ADMIN` собственный аккаунт.

## 5. Сквозной пользовательский сценарий

```text
Лендинг
  → модальное окно входа через Google и принятие документов
  → OAuth callback находит пустой draft или создаёт проект
  → /app/<projectId>: полный холст с настройками и компактной загрузкой фотографии
  → фотография появляется на холсте
  → разметка + референсы + текст + комната + стиль + формат
  → резерв 4 кредитов
  → генерация QUEUED → PROCESSING → SUCCEEDED
  → просмотр/скачивание результата
  → выбор результата → текстовая/визуальная доработка
  → новый резерв 4 кредитов → дочерняя генерация
```

Если возникает техническая ошибка, резерв возвращается автоматически. Если queued-задача отменена, выполняется cancellation refund. История вариантов не перезаписывается.

## 6. Публичные страницы

### 6.1. Лендинг `/en`, `/ru`, `/uz`

Цель страницы — объяснить ценность продукта и привести пользователя к первому проекту.

Лендинг доступен на английском, русском и узбекском языках по стабильным URL. Корневой `/` выбирает язык по `Accept-Language`; неподдерживаемый или отсутствующий язык ведёт на английскую версию. Прямые локализованные URL не перенаправляются. Выбранная локаль сохраняется в cookie `NEXT_LOCALE` и применяется к `/login`, `/app`, юридическим документам, защищённым пользовательским сценариям, общим loading/error-состояниям и accessibility-подписям. Клиентские границы защищённого приложения при этом не меняются. Английская и узбекская версии юридических документов являются переводами; при расхождениях применяется русская версия.

Структура сверху вниз:

1. Sticky header:
   - логотип ведёт на `/`;
   - якоря «Примеры», «Как это работает», «Пакеты»;
   - действие «Войти» открывает модальное окно входа без ухода с лендинга;
   - header и основные секции используют единый контейнер до `1440px`;
   - на desktop секции занимают единый экранный кадр до Full HD, а на меньших экранах переходят на естественную высоту.
2. Hero:
   - обещание AI-интерьера из фотографии;
   - CTA открывает вход в модальном окне, а для вошедшего пользователя — `/app`;
   - ссылка на примеры;
   - пояснение про 10 стартовых кредитов, отсутствие карты, приватное хранение, 6 стилей и текстовые правки.
3. Примеры:
   - демонстрация гостиных, кухни, спальни, кабинета и столовой в разных стилях.
4. Процесс:
   - добавить фотографию;
   - описать желаемое и выбрать стиль;
   - развивать понравившийся результат.
5. Пользовательские сценарии:
   - ремонт;
   - работа дизайнера;
   - подготовка объекта к продаже;
   - обновление отдельной комнаты.
6. Объяснение единого холста:
   - исходник и варианты остаются рядом;
   - правки задаются текстом;
   - история не теряется.
7. Пакеты кредитов:
   - загружаются из публичного API;
   - отображаются только активные пакеты;
   - популярный пакет выделяется;
   - рассчитывается число полных генераций из цены одной генерации;
   - «Купить» открывает вход в модальном окне, затем ведёт на `/app/credits`.
8. FAQ:
   - требования к фото;
   - сохранение геометрии;
   - дочерние доработки;
   - стоимость генерации;
   - возврат при технической ошибке;
   - стартовые кредиты.
9. Финальный CTA открывает вход в модальном окне или `/app` при активной сессии.
10. Footer:

- продуктовые якоря;
- вход;
- юридические документы;
- `support@ruvie.cc`.

Состояния каталога пакетов:

- loading — skeleton-карточки;
- error — сообщение и «Повторить»;
- success — сетка актуальных пакетов.

### 6.2. Вход `/login`

На лендинге основные CTA и ссылки входа используют ту же форму внутри модального окна. Отдельный `/login` остаётся для прямых ссылок и возврата после ошибки OAuth. Закрытие модального окна не меняет страницу; юридическое согласие обязательно и в модальном окне.

Флоу:

1. Страница проверяет существующую сессию.
2. Если сессия уже есть, пользователь автоматически возвращается на безопасный `next` URL, по умолчанию `/app`.
3. Без сессии пользователь должен отметить checkbox принятия публичной оферты и политики конфиденциальности.
4. До принятия документов кнопка Google заблокирована.
5. При нажатии формируется OAuth URL с:
   - безопасным `next`;
   - текущим origin;
   - версиями принятых юридических документов.
6. После callback сервер создаёт/обновляет профиль, фиксирует принятие документов, создаёт кошелёк и стартовое начисление при необходимости.
7. Для `next=/app` callback транзакционно находит или создаёт пустой проект и сразу направляет на `/app/<projectId>`. При ошибке entry operation авторизованная сессия сохраняется, а `/app` позволяет повторить попытку. Для других защищённых URL сохраняется исходный `next`.

`next` принимается только как локальный путь, начинающийся с одного `/`; внешние, protocol-relative и содержащие управляющие символы значения заменяются на `/app`.

### 6.3. Юридические страницы `/privacy` и `/offer`

Страницы рендерят Markdown из `docs/legal/` и являются публичными. Текущие версии документов участвуют в записи `LegalAcceptance` при OAuth-входе.

## 7. Общая защищённая оболочка

Любой маршрут `/app` обёрнут в проверку сессии:

- пока идёт проверка — «Проверяем сессию…»;
- при `401` — redirect на `/login?next=<текущий URL>`;
- при временной/сетевой ошибке — сессия не сбрасывается автоматически, показывается retry;
- после успеха в React context доступны пользователь и кошелёк.

Навигация dashboard-страниц:

- «Создать» → `/app`;
- «Профиль» → `/app/profile`;
- «Кредиты» → `/app/credits`;
- текущий баланс виден в header.

Workspace `/app/[id]` использует компактный header и занимает всю доступную высоту окна.

## 8. Вход в проект `/app`

Это не каталог и не отдельный мастер. Страница выполняет entry operation:

После Google OAuth с `next=/app` та же операция выполняется в callback, чтобы открыть холст без промежуточной страницы. `/app` остаётся точкой входа для уже авторизованных пользователей и резервным маршрутом при ошибке callback entry.

1. Сервер транзакционно блокирует entry пользователя.
2. Ищет принадлежащий пользователю пустой draft без исходной фотографии.
3. Если такой draft существует — возвращает его.
4. Иначе создаёт новый проект с именем по умолчанию.
5. Клиент заменяет URL на `/app/<projectId>`.

Так предотвращается создание нескольких пустых проектов из-за повторных кликов или параллельных запросов.

Состояния:

- загрузка — «Открываем рабочее пространство…»;
- ошибка — сообщение и «Повторить»;
- успех — бесшовный redirect.

## 9. Рабочее пространство `/app/[id]`

### 9.1. Загрузка workspace

При открытии загружаются проект, source, первоначальные референсы и начальный набор генераций.

Состояния:

- loading — skeleton холста и инспектора;
- `404` — «Проект не найден» и ссылка «Все проекты»;
- другая ошибка — retry и ссылка на каталог;
- проект без source — полный холст с инспектором и компактной зоной загрузки;
- проект с source — полноценный canvas workspace.

### 9.2. Загрузка исходной фотографии

До загрузки исходника инспектор уже доступен: можно ввести описание, выбрать комнату, стиль и формат. Генерация заблокирована до появления фото. Эти настройки сохраняются в состоянии рабочего пространства при переходе от пустого холста к холсту с загруженной фотографией.

Пользователь может выбрать файл или перетащить его в drop zone.

Клиент принимает:

- JPEG;
- PNG;
- WebP;
- не более 15 МБ.

Сервер дополнительно проверяет:

- MIME по содержимому;
- минимум 512×512 px;
- максимум 6000 px по стороне;
- корректность изображения;
- соответствие интерьерной сцене в Vertex production-режиме.

Допускаются жилые и коммерческие интерьеры, пустые помещения и черновой ремонт. Экстерьеры, фасады, улицы и неоднозначные сцены могут быть отклонены.

Технический флоу загрузки:

1. Клиент валидирует тип и размер.
2. Получает разрешение на staged upload.
3. Загружает файл в приватный `staging-uploads` с прогрессом.
4. Передаёт идентификатор staged upload endpoint проекта.
5. Сервер повторно проверяет владельца, назначение, срок, размер и содержимое.
6. Создаёт original и preview, нормализует EXIF orientation.
7. Привязывает source к проекту.
8. Workspace query обновляется, и без смены страницы открывается холст.

Source можно прикрепить только один раз. Повторная попытка получает `409 SOURCE_ALREADY_EXISTS`.

Загрузку можно отменить. Ошибка сохраняет возможность выбрать файл повторно.

### 9.3. Холст

На холсте находятся:

- исходная фотография;
- карточки всех загруженных поколений генераций;
- связи/пространственное расположение вариантов;
- плавающая панель разметки;
- inspector параметров;
- onboarding.

Пользователь может выбирать source или успешный результат. Выбор результата открывает контекстное действие «Доработать». Кнопка «Открыть» показывает полноэкранный просмотр результата.

Старые варианты загружаются порциями. Если есть `nextCursor`, появляется действие «Загрузить предыдущие варианты» с числом уже загруженных и общим количеством.

### 9.4. Инструменты разметки

Доступны:

- select — выбор объектов и перемещение холста;
- pen — ручка;
- marker — полупрозрачный маркер;
- rectangle — прямоугольное выделение;
- eraser — стирание разметки;
- цвет из пресетов или произвольный цвет;
- отдельная толщина линии и ластика;
- undo;
- redo;
- полная очистка разметки.

Очистка source-разметки:

- не удаляет фотографию;
- не удаляет проект, референсы или генерации;
- очищает canvas state и visual prompt;
- сразу сохраняется на сервере.

Очистка refinement-разметки очищает только временное состояние редактора выбранного результата.

Надёжность черновика:

- Fabric JSON сохраняется в IndexedDB;
- localStorage используется как синхронная резервная копия;
- серверное сохранение выполняется с debounce;
- экспорт overlay и HTTP persistence используют разные очереди;
- offline/сетевая ошибка не блокирует рисование;
- при восстановлении учитывается версия server state;
- данные изолированы по пользователю и проекту;
- явный logout очищает локальные draft-данные.

### 9.5. Inspector генерации

Inspector расположен справа на desktop и открывается как адаптивная панель на малых экранах.

#### Референсы

Можно:

- загрузить JPEG/PNG/WebP;
- импортировать одну или несколько ссылок, по одной на строку;
- открыть preview в новой вкладке;
- переставить референс влево/вправо;
- удалить один референс;
- очистить весь список.

Ограничения:

- максимум 10 изображений;
- до 15 МБ на файл;
- минимум 128×128 px;
- максимум 6000 px по стороне;
- URL import защищён от SSRF, private IP, unsafe redirects, timeout и чрезмерного ответа;
- частично успешный URL import сохраняет успешные элементы и сообщает первую ошибку.

Порядок референсов является бизнес-данными и фиксируется в snapshot генерации.

#### Текстовое описание

- обязательное поле;
- после trim минимум 3 символа;
- максимум 4000 символов;
- счётчик длины виден постоянно;
- пример в placeholder объясняет желаемую формулировку.

#### Тип комнаты

- обязателен для каждой новой корневой генерации;
- список загружается с сервера и содержит только активные типы;
- пользователь видит название, но не скрытый server-side prompt modifier;
- выбор сбрасывается после успешного резервирования root generation;
- если выбранный тип был отключён, UI сбрасывает выбор и обновляет каталог.

#### Стиль

Выбор необязателен. Доступны:

- Современный;
- Джапанди;
- Минимализм;
- Неоклассика;
- Лофт;
- Скандинавский.

Повторный клик по выбранному стилю снимает выбор. В backend передаётся allowlisted code, а не произвольная AI-инструкция.

#### Формат

По умолчанию выбран «Как в исходнике»: фактические размеры фотографии сопоставляются с ближайшим поддерживаемым форматом.

Доступны:

- `1:1`;
- `16:9`;
- `9:16`;
- `4:3`;
- `3:4`.

Формат фиксируется в конкретной генерации. Refinement наследует формат родителя и не предлагает новый выбор.

#### Кнопка генерации

Показывает стоимость операции и недоступна, если:

- уже отправляется запрос;
- prompt короче 3 или длиннее 4000 символов;
- каталог комнат загружается или недоступен;
- нет активных типов комнат;
- комната не выбрана;
- баланс недоступен;
- недостаточно кредитов.

При недостаточном балансе пользователь получает ссылку на `/app/credits`.

### 9.6. Onboarding холста

Onboarding можно запустить повторно кнопкой «Как работать». Он состоит из шести шагов:

1. Общая механика холста.
2. Инструменты рисования.
3. Референсы.
4. Стиль.
5. Запуск генерации.
6. Доработка результата.

Onboarding ничего не запускает автоматически. Его можно пропустить; факт завершения хранится в профиле по версии onboarding.

## 10. Генерации

### 10.1. Root generation

До создания сервер проверяет:

- активного пользователя;
- владельца проекта;
- наличие source;
- активность выбранной комнаты;
- валидность prompt, style и aspect ratio;
- глобальный emergency stop;
- лимит параллельных генераций пользователя;
- достаточный баланс;
- валидный `Idempotency-Key`.

Создание выполняется транзакционно:

1. Сохраняется актуальная source-разметка.
2. Формируется неизменяемый snapshot входов.
3. Создаётся `Generation` в `QUEUED`.
4. Создаётся `UsageEvent` в `RESERVED` на 4 кредита.
5. Из кошелька списываются 4 кредита.
6. Создаётся `CreditTransaction` типа `GENERATION_DEBIT`.
7. Клиент добавляет карточку на холст и обновляет баланс.

Клиент хранит ключ попытки в sessionStorage вместе с хешем входов. Если ответ потерян из-за сети, повтор с теми же входами использует тот же ключ и не создаёт двойное списание.

### 10.2. Статусы и UI

| Статус       | Смысл                             | Действия пользователя                                            |
| ------------ | --------------------------------- | ---------------------------------------------------------------- |
| `QUEUED`     | Резерв создан, задача ждёт worker | Отменить                                                         |
| `PROCESSING` | Provider создаёт изображение      | Ожидать; результат появится автоматически                        |
| `SUCCEEDED`  | Result сохранён                   | Выбрать, открыть, скачать, доработать                            |
| `FAILED`     | Техническая ошибка                | Повторить                                                        |
| `REJECTED`   | Запрос отклонён проверкой         | Исправить текущие параметры и запустить заново через «Повторить» |
| `CANCELLED`  | Задача отменена до исполнения     | Нет повторного запуска этой записи                               |

Для активных состояний показывается прошедшее время. Ошибки загрузки signed URL результата можно повторить отдельно, не создавая новую генерацию.

### 10.3. Выполнение worker

Worker:

1. Атомарно захватывает queued-задачу.
2. Переводит её в `PROCESSING`.
3. Загружает приватные входные изображения.
4. Собирает final prompt из системной инструкции, комнаты, стиля и пользовательского текста.
5. Вызывает fake или Vertex provider.
6. Нормализует результат и сохраняет lossless WebP original/user result.
7. Переводит запись в `SUCCEEDED`.
8. Переводит usage из `RESERVED` в `CONSUMED`.

Provider и model ID выбирает только сервер:

- `AI_PROVIDER=fake` — локальная детерминированная имитация;
- `AI_PROVIDER=vertex` — Google Vertex AI;
- пользователь не может выбрать модель или передать credentials.

### 10.4. Ошибка, возврат и отмена

При технической ошибке:

- частично загруженные результаты удаляются или ставятся в очередь удаления;
- сохраняются безопасные error code/message;
- генерация получает terminal status;
- usage становится `REFUNDED`;
- кошелёк пополняется на зарезервированную сумму;
- записывается `TECHNICAL_REFUND`.

Отмена допустима для состояния, которое сервер ещё может безопасно отменить. При успешной отмене выполняется идемпотентный `CANCELLATION_REFUND`.

Terminal generation не возвращается в `PROCESSING`.

### 10.5. Retry

Для `FAILED` клиент отправляет retry исходной записи с новым namespaced idempotency key. Сервер повторно использует сохранённый snapshot и создаёт новую попытку без изменения старой записи.

Для `REJECTED` интерфейс запускает новую root generation из актуальных параметров инспектора, потому что пользователь должен иметь возможность изменить описание, разметку, стиль или комнату.

Повтор защищён от двойного списания.

### 10.6. Просмотр и скачивание

Действие «Открыть» показывает modal на полный экран/широкую карточку с:

- изображением;
- кнопкой скачивания;
- форматом;
- разрешением;
- исходным пользовательским описанием;
- датой создания.

Download endpoint проверяет владельца и отдаёт сохранённый WebP без повторной конвертации и потери качества.

### 10.7. Доработка результата

Дорабатывать можно только успешную генерацию с `resultOriginal`.

Флоу:

1. Пользователь выбирает успешную карточку.
2. При необходимости рисует новую разметку поверх результата.
3. Нажимает «Доработать».
4. Вводит prompt 3–4000 символов.
5. Может добавить до 10 новых локальных референсов.
6. Отправляет операцию стоимостью 4 кредита.
7. Создаётся новая дочерняя `Generation` с `parentGenerationId`.
8. Новая карточка появляется на холсте, родитель не меняется.

Refinement:

- использует чистый `resultOriginal` родителя как основной source;
- наследует aspect ratio, style и snapshot комнаты;
- не наследует project references и references родителя автоматически;
- получает только новые референсы из composer;
- использует только новую разметку;
- нормализует результат к точным пиксельным размерам родителя.

Текст refinement сохраняется в localStorage как draft до успешной отправки. При ошибке prompt и выбранные файлы остаются для повтора в текущем открытом composer.

## 11. Каталог проектов `/app/projects`

Каталог показывает только проекты, в которых есть хотя бы одна успешная генерация с сохранённым original result. Пустые и незавершённые draft-проекты в каталоге не видны, но остаются в базе.

Функции страницы:

- создание нового проекта;
- серверный поиск по названию;
- debounce поиска 300 мс;
- URL-параметры `search` и `page`;
- очистка поиска;
- вид grid/list;
- пагинация по 20 проектов;
- открытие workspace;
- удаление проекта через подтверждение.

Карточка показывает:

- preview результата;
- название;
- дату обновления;
- число результатов.

Удаление является необратимым с точки зрения UI: проект и связанные изображения удаляются/помечаются на удаление. При удалении единственного элемента не первой страницы интерфейс переходит на предыдущую страницу.

Пустые состояния различают:

- у пользователя ещё нет завершённых проектов;
- поиск ничего не нашёл;
- текущая страница пуста.

## 13. Кредиты `/app/credits`

### 13.1. Баланс и стоимость

- новый пользователь получает 10 кредитов один раз;
- root generation стоит 4 кредита;
- refinement стоит 4 кредита;
- отрицательный баланс запрещён;
- кредиты не сгорают;
- технические и cancellation ошибки возвращают резерв автоматически.

### 13.2. Пакеты

Публичная витрина показывает активные пакеты в `sortOrder`. Карточка содержит название, описание, цену, кредиты, число полных генераций и отметку популярного пакета.

Название и описание пакета поддерживают RU/EN/UZ. Публичный API выбирает текст по `Accept-Language`; при отсутствии узбекского перевода используется английский, а для legacy-записей без английского — прежнее русское значение. Заказ сохраняет локализованные snapshot-названия, поэтому последующее редактирование пакета не меняет историю.

При нажатии «Купить»:

1. Проверяется, что покупки включены.
2. Создаётся `PaymentOrder` со snapshot пакета.
3. Изменение/удаление пакета после этого не меняет созданный заказ.
4. Клиент переходит на `checkoutUrl`.

Режимы:

- `disabled` — кнопки покупки заблокированы, показано «Оплата временно недоступна»;
- `mock` — показано предупреждение о тестовом режиме;
- production Payme/Click в текущей реализации отсутствует.

### 13.3. Журнал операций

Показываются тип, дата, изменение и баланс после операции.

Типы:

- `SIGNUP_GRANT` — стартовое начисление;
- `PURCHASE` — покупка;
- `GENERATION_DEBIT` — списание за генерацию;
- `TECHNICAL_REFUND` — возврат при технической ошибке;
- `CANCELLATION_REFUND` — возврат при отмене;
- `ADMIN_ADJUSTMENT` — ручная корректировка.

### 13.4. Mock checkout `/app/credits/checkout/[id]`

Доступен только в безопасной локальной конфигурации: не production и `AI_PROVIDER=fake`.

Страница показывает snapshot заказа и позволяет симулировать:

- `PAID` — кредиты начисляются один раз, затем предлагается вернуться в приложение;
- `FAILED` — заказ завершается ошибкой;
- `CANCELLED` — заказ отменяется.

Во время outcome/reconciliation controls блокируются. Клиент повторно сверяет заказ и баланс, чтобы не показать успех до подтверждённого зачисления.

Переходы `PaymentOrder`:

```text
PENDING → PAID | FAILED | CANCELLED | EXPIRED
```

Из terminal status переходов нет. Повтор provider event и повторное зачисление защищены idempotency.

## 14. Административная панель

### 14.1. Общая оболочка

После входа доступны sidebar, header, avatar администратора, переключение light/dark темы и logout.

На mobile sidebar открывается burger-кнопкой. После навигации focus переносится на заголовок новой страницы. Если сессия отсутствует — redirect на `/login`. Если профиль существует, но не является активным администратором, показывается «Нет доступа» и возможность войти другим аккаунтом.

### 14.2. Административный вход `/login`

Production-флоу:

1. Ввод единого кода минимум из 5 символов.
2. Backend применяет rate limit и сравнивает код с server secret.
3. При успехе возвращается подписанный admin-token на 8 часов.
4. Frontend хранит token локально.
5. Каждый запуск панели проверяет token и актуальные роль/статус через `/admin/session`.

В development доступен альтернативный вход по телефону формата `+998XXXXXXXXX`. В production `AdminPhone` запрещён.

### 14.3. Dashboard `/`

Периоды: сегодня, 7 дней, 30 дней. Выбор сохраняется в query `period`.

Карточки:

- всего пользователей;
- активные пользователи;
- генерации за период;
- ошибки за период;
- queued;
- processing.

Графики:

- area chart генераций по дням;
- donut статусов `QUEUED`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `REJECTED`.

### 14.4. Пользователи `/users`

Фильтры и навигация:

- поиск по имени, email или телефону;
- роль `USER`/`ADMIN`;
- статус `ACTIVE`/`BLOCKED`/`DELETED`;
- page size 25/50/100;
- server pagination.

Таблица показывает аккаунт, email/телефон, роль, баланс, статус, дату регистрации и действия.

Действия:

- открыть карточку;
- изменить роль;
- изменить статус;
- скорректировать баланс.

Понижение `ADMIN` до `USER`, блокировка и удаление активного пользователя требуют дополнительного подтверждения, так как могут немедленно лишить доступа.

Кредитная корректировка:

- только целое ненулевое значение;
- диапазон UI от −100000 до 100000;
- положительное число начисляет;
- отрицательное списывает и требует подтверждения;
- причина обязательна, минимум 3 символа;
- создаётся `ADMIN_ADJUSTMENT`;
- используется стабильный idempotency key попытки;
- баланс не может стать отрицательным.

### 14.8. Комнаты `/rooms`

Тип комнаты содержит:

- неизменяемый после создания code;
- пользовательское название;
- английский и optional узбекский варианты пользовательского названия;
- скрытый prompt modifier для AI;
- active;
- sort order.

Создание/редактирование:

- code — 2–32 символа, lowercase letters, digits, hyphen;
- name — минимум 2 символа, максимум 80;
- английское name — обязательно, узбекское — optional;
- prompt modifier — минимум 10, максимум 2000;
- меньший sort order отображается раньше;
- active определяет доступность для новых root generation.

Удаление в UI означает мягкое отключение:

- комната исчезает из новых пользовательских генераций;
- существующие генерации и refinements продолжают использовать snapshot;
- повторное включение выполняется редактированием;
- сервер не позволяет отключить последнюю активную комнату.

### 14.11. Пакеты `/finance/packages`

Пакет содержит:

- неизменяемый code;
- name;
- description;
- английские и optional узбекские варианты name/description;
- credits;
- price UZS;
- popular;
- active;
- sort order.

Валидация:

- code — 2–32 lowercase letters/digits/hyphen;
- name — минимум 2 символа;
- credits — положительное целое;
- цена — от 1 000 UZS;
- popular возможен только для active;

Действия:

- создать;
- редактировать все поля кроме code;
- отключить через `active=false`;

Удаление убирает пакет из продажи, но не меняет snapshot и историю уже созданных заказов.

## 15. Доменные модели и связи

### Profile

Пользователь приложения. Хранит email/phone, имя, роль, статус, timezone, последнюю активность и состояние onboarding.

### LegalAcceptance

Факт принятия конкретных версий политики и оферты при OAuth-входе.

### Project

Контейнер исходной фотографии, визуальной разметки, project references и дерева генераций. Статусы: `DRAFT`, `READY`, `ARCHIVED`.

### MediaFile

Метаданные приватного файла. Типы: source, source preview, visual prompt, reference, generation original, generation result.

### ProjectReference

Упорядоченная связь проекта и reference file, с optional source URL.

### Generation

Неизменяемый snapshot AI-операции: пользователь, проект, parent, prompt, room snapshot, style, format, source, visual prompt, результаты, provider metadata, timing, cost и status.

### GenerationReference

Упорядоченный snapshot references конкретной генерации.

### RoomType

Управляемый администратором тип комнаты и скрытая AI-инструкция.

### UsageEvent

Жизненный цикл кредитного резерва: `RESERVED`, `CONSUMED`, `REFUNDED`, `EXPIRED`.

### CreditWallet

Один транзакционный баланс на пользователя.

### CreditTransaction

Неизменяемое движение кредита с `balanceAfter` и idempotency key.

### CreditPackage

Управляемое предложение витрины.

### PaymentOrder

Неизменяемый snapshot пакета и жизненный цикл оплаты.

### PaymentEvent

Идемпотентное событие provider-а, уникальное по provider/event ID.

## 16. API

Все API-ответы используют единый envelope с `requestId`. Validation errors не содержат stack trace или secrets.

Пользовательский frontend передаёт выбранный `NEXT_LOCALE` как `Accept-Language`. Публичный API локализует безопасный `error.message`, validation details и отображаемые каталоговые поля для `ru`, `en` и `uz`, сохраняя стабильный `error.code` и HTTP-статус. Неподдерживаемый язык использует английский fallback. Admin API и интерфейс админки остаются русскоязычными.

Типичные статусы ошибок:

- `400` — malformed request или бизнес-валидация;
- `401` — отсутствует/истекла сессия;
- `402` — недостаточно кредитов;
- `403` — нет доступа, пользователь заблокирован или origin запрещён;
- `404` — объект не найден или не принадлежит пользователю;
- `409` — конфликт состояния;
- `422` — schema validation;
- `429` — rate limit.

## 17. Безопасность и приватность

- Supabase JWT проверяется на backend.
- Статус профиля проверяется для каждой защищённой бизнес-операции.
- Все пользовательские Prisma queries owner-scoped.
- Бизнес-таблицы не изменяются через Supabase Data API.
- Медиа хранится в приватных buckets.
- Signed URLs короткоживущие и выдаются только владельцу или администратору.
- Upload проверяется по реальному MIME, размеру и геометрии.
- URL importer защищён от SSRF.
- CORS использует exact allowlist `APP_ORIGINS` и `ADMIN_ORIGINS` без wildcard.
- Refresh token хранится в HttpOnly cookie; access token передаётся как Bearer.
- Mock payments и AdminPhone запрещены в production.
- Prompt, cookies, изображения, signed URLs и secrets исключаются из telemetry.
- Дорогие и административные mutations защищены rate limit.

## 18. Системные лимиты

| Переменная                 | По умолчанию | Назначение                           |
| -------------------------- | -----------: | ------------------------------------ |
| `MAX_PARALLEL_GENERATIONS` |            1 | Одновременные генерации пользователя |
| `MAX_REFERENCE_IMAGES`     |           10 | Референсы проекта/refinement         |
| `MAX_REFERENCE_URLS`       |           10 | URL за импорт                        |
| `MAX_UPLOAD_SIZE_MB`       |           15 | Размер изображения                   |
| `MAX_OUTPUT_WIDTH`         |         4096 | Максимальная ширина результата       |
| `MAX_OUTPUT_HEIGHT`        |         4096 | Максимальная высота результата       |

Все пользователи имеют одинаковые лимиты. Тарифов, подписок, VIP-исключений, дневной квоты и пользовательского выбора AI-модели нет.

Операторский emergency stop:

```dotenv
GENERATIONS_ENABLED=false
```

Новые AI-операции получают безопасное сообщение о временной приостановке; существующие данные не удаляются.

## 19. Хранение и очистка

Приватные buckets:

- `source-images`;
- `visual-prompts`;
- `reference-images`;
- `generation-originals`;
- `generation-results`;
- `branding`;
- `staging-uploads` для временной прямой загрузки.

Временные staged uploads имеют владельца, назначение и срок действия. Просроченные файлы и неудачные удаления обрабатываются maintenance-командой. Повторные удаления хранятся в `StorageDeletion` с attempts/nextAttemptAt.

## 20. Что не реализовано

- production payments Payme/Click;
- подписки и тарифные планы;
- выбор AI-модели пользователем;
- удаление отдельного результата генерации;
- ручное редактирование snapshot генерации;
- permanent admin audit log;
- системные уведомления;
- таблица глобальных настроек;
- индивидуальные лимиты/VIP;
- автоматическая очистка всех скрытых незавершённых проектов;
- обязательный Trigger.dev;
- обязательный Sentry runtime.

## 21. Проверка ключевых флоу

Минимальная функциональная приёмка:

1. Google OAuth, обязательное принятие документов и возврат на `next`.
2. Стартовое начисление 10 кредитов создаётся ровно один раз.
3. `/app` не плодит параллельные пустые draft-проекты.
4. Source upload: drag/drop, progress, cancel, invalid type/size, server validation.
5. Разметка: pen, marker, rectangle, eraser, undo, redo, clear, reload и offline draft.
6. References: files, URLs, partial failure, reorder, delete, clear, limit 10.
7. Обязательная комната, optional style, пять форматов и source ratio.
8. Root generation: reservation, duplicate request, polling, success и download.
9. Technical failure и cancellation возвращают кредиты ровно один раз.
10. Retry не дублирует списание.
11. Refinement наследует snapshot и использует только новые references/markup.
12. Каталог: search, clear, grid/list, pagination, delete.
13. Профиль: update name, copy email, logout.
14. Credits: packages, disabled/mock mode, transactions, checkout reconciliation.
15. Admin login, expired token и forbidden state.
16. Admin user update, self-lockout protection и idempotent balance adjustment.
17. Admin generation filters, detail media и cancel.
18. Room create/edit/deactivate и защита последней активной комнаты.
19. Package create/edit/delete и snapshot старых orders.
20. Responsive и keyboard UX на 375, 768 и 1440 px.
