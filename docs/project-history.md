# История проекта Renoa

- Статус документа: сводная история разработки на 1 августа 2026 года.
- Источник истины для текущего поведения: код ветки `master` на коммите `e952653`.
- Назначение: объединить решения из `.superpowers`, `docs/superpowers`, Git-истории и текущей реализации в один читаемый документ.

## 1. Откуда собрана история

При подготовке были изучены все материалы из двух групп:

- `docs/superpowers/specs` — согласованные продуктовые и архитектурные решения;
- `docs/superpowers/plans` — поэтапные планы реализации;
- `.superpowers/brainstorm` — интерактивные варианты интерфейса и выбранные направления;
- `.superpowers/sdd` — задания исполнителям, отчёты, промежуточные и финальные code review diff;
- Git-история с 20 июля по 1 августа 2026 года;
- текущие маршруты, Prisma-схема, серверные сервисы, клиентское приложение и отдельная админ-панель.

После консолидации каталоги `superpowers` были удалены из рабочей копии. Отслеживавшиеся спецификации и планы при необходимости восстанавливаются из Git. Локальные `review-*.diff` дублировали изменения, уже сохранённые в Git; их ценность состояла в доказательстве последовательных проверок, а не в описании текущего API.

## 2. Исходная идея

Проект начался как веб-сервис AI-визуализации интерьера по фотографии помещения. Основной сценарий был определён сразу:

1. пользователь входит в систему;
2. создаёт проект и загружает фотографию комнаты;
3. добавляет текстовое описание, визуальную разметку и изображения-референсы;
4. сервер формирует безопасный prompt и запускает AI-генерацию;
5. пользователь получает результат, сравнивает его с исходником, скачивает и хранит в истории;
6. тарифы, лимиты и административные функции контролируют доступ и стоимость операций.

Главный продуктовый инвариант не менялся: AI должен обновлять интерьер, сохраняя ракурс, геометрию комнаты, расположение стен, окон, дверей и основные пропорции.

## 3. 20–22 июля: фундамент платформы

### 3.1. Документы и каркас

20 июля появились исходное ТЗ, архитектурный дизайн и планы фундамента. Проект был создан как Next.js App Router приложение на TypeScript с тёмной темой, единым REST-envelope и request ID.

Были приняты базовые решения:

- Prisma — единственный слой доступа к бизнес-данным PostgreSQL;
- Supabase используется для Auth и приватного Storage;
- секреты и вызовы AI доступны только серверу;
- данные каждого пользователя изолируются owner-проверками;
- медиа хранятся в приватных buckets и выдаются по короткоживущим signed URL;
- локальная разработка не должна зависеть от реального AI, поэтому предусмотрен fake provider.

### 3.2. Пользователи, проекты и медиа

В первых рабочих коммитах появились:

- профиль пользователя и роли `USER`/`ADMIN`;
- тарифы `FREE` и `VIP`;
- создание, просмотр, изменение, архивирование и дублирование проектов (изменение и дублирование позднее удалены при упрощении MVP);
- загрузка исходного изображения с проверкой типа, размера и геометрии;
- приватное хранение оригинала и preview;
- файловые и URL-референсы с порядком отображения;
- SSRF-защита импорта внешних URL;
- Visual Prompting на базе Fabric.js;
- история генераций и профиль;
- административные API и базовые security headers/rate limits.

### 3.3. Первая генерация

Generation Core ввёл атомарное резервирование дневного лимита, idempotency key, неизменяемый снимок входных данных генерации, fake provider и жизненный цикл:

`QUEUED → PROCESSING → SUCCEEDED | FAILED | REJECTED | CANCELLED`.

При ошибке резерв использования возвращался. Результаты сохранялись отдельно как оригинал AI и пользовательская версия с учётом watermark-политики тарифа.

22 июля был подключён Google Vertex AI. Позже модель была переключена на Gemini image generation. Внешние идентификаторы и credentials остались серверными.

## 4. 24 июля: canvas-first workspace

### 4.1. Выбор интерфейса

В `.superpowers/brainstorm` сравнивались три макета редактора:

- холст с правой панелью;
- холст с нижним dock;
- студия с переключаемыми режимами.

Выбран подход «холст + правая панель»: изображение и результаты остаются центром работы, инструменты рисования вынесены наружу, а настройки AI находятся в постоянном инспекторе.

### 4.2. Реализация рабочего пространства

Большой SDD-цикл разделил работу на шесть частей:

1. каталог интерьерных стилей и серверная композиция prompt;
2. единый контракт данных workspace;
3. pan/zoom-холст и внешняя панель аннотаций;
4. постоянный AI-инспектор;
5. placeholders, карточки результатов, сравнение и скачивание;
6. адаптивность, доступность и итоговая проверка.

Появились шесть стилей: современный, джапанди, минимализм, неоклассика, лофт и скандинавский. Код стиля сохраняется в снимке генерации, а сервер добавляет соответствующий модификатор к prompt.

### 4.3. Надёжность холста

Последовательные review-волны исправили несколько сложных классов ошибок:

- гонки между сохранением, очисткой, undo/redo и запуском генерации;
- неправильные координаты старых Fabric-объектов после изменения размера редактора;
- искажение `strokeUniform` при неравномерном масштабировании;
- нестабильную нумерацию вариантов при пагинации;
- отсутствие обновления лимита после возврата;
- недоступные touch targets и незаметный keyboard focus.

Финальное решение сериализует публичные операции холста через FIFO. Старые uniform strokes при миграции растеризуются с прозрачным padding и измерением alpha bounds, чтобы сохранить визуальный результат.

Локальные отчёты отмечают, что статические проверки и build прошли, но часть authenticated browser verification оставалась недоступной без живого сеанса. Это историческое ограничение проверки, а не незавершённая задача в текущем backlog.

## 5. 25 июля: упрощение маршрутов

Первоначальная многостраничная схема редактора была заменена на прямой вход:

- `/app` создаёт или выбирает проект;
- `/app/[id]` — канонический единый workspace;
- старые `/app/design` и `/app/design/[id]` сначала сохранялись как совместимые перенаправления, а после перехода всех ссылок на канонический маршрут были удалены.

Пустой проект и проект с фотографией стали двумя состояниями одного экрана. Пользователь больше не проходит отдельный мастер перед открытием редактора.

В этот же период были исправлены production build на Vercel, генерация Prisma Client и упаковка Linux runtime для Sharp.

## 6. 26 июля: загрузка на холсте и постоянная сессия

Загрузка исходной фотографии была перенесена непосредственно в workspace. Были реализованы:

- немедленная загрузка выбранного файла;
- защита от устаревших ответов и отмена запроса;
- замена исходной фотографии без выхода из проекта;
- единая политика приватных маршрутов;
- обновление Supabase-сессии через proxy;
- сохранение авторизации при переходах между публичными и приватными страницами.

Отдельный этап добавил серверную конвертацию успешных результатов в JPEG при скачивании. В Storage при этом продолжают храниться WebP-объекты.

## 7. 26–28 июля: итеративные доработки результата

### 7.1. Продуктовое решение

Второй brainstorm сравнивал:

- чат в правой панели;
- отдельное поле под каждым результатом;
- форму внутри окна результата;
- один универсальный блок для выбранного результата.

После промежуточного варианта «редактор у каждого результата» был согласован универсальный composer, работающий с выбранной успешной генерацией.

### 7.2. Дерево генераций

Модель данных получила `parentGenerationId`. Каждая доработка создаёт новый неизменяемый snapshot и наследует базовые параметры родителя. Пользователь может:

- выбрать успешный результат;
- добавить новый prompt;
- добавить временные reference-файлы;
- нарисовать новую разметку;
- создать дочерний вариант;
- продолжить работу от любой успешной ветки.

Выбор AI-модели был удалён из клиентского интерфейса. Сервер стал единственным владельцем provider/model configuration. Это отменило более раннее решение о таблице доступных моделей и пользовательском `modelCode`.

Для снижения нагрузки полное дерево не опрашивается каждые 1,5 секунды: новые задачи отслеживаются точечно, а коллекция обновляется по завершению.

### 7.3. Плавающий composer

28 июля форма доработки была вынесена из масштабируемой карточки результата в screen-space overlay. Контекстная панель привязана к выбранной карточке, но не масштабируется вместе с холстом. На мобильных устройствах она адаптируется к доступному viewport.

## 8. 29 июля: продуктовый интерфейс Renoa

Проект получил имя Renoa и цельный тёмный визуальный язык:

- графитовый фон, лаймовый акцент и Geist;
- единая навигация приложения;
- обновлённые landing и login;
- переработанные workspace, история, профиль и кредиты;
- общие UI primitives;
- адаптивная верхняя панель и мобильная навигация.

Затем восемь самописных primitives были мигрированы на registry-реализации shadcn/ui с Radix. Для совместимости сохранены Renoa-варианты `primary`, `success`, `warning`, а мобильная навигация переведена с native dialog на Sheet.

## 9. 29 июля: кредиты и mock-платежи

Презентационный баланс превратился в транзакционную финансовую подсистему:

- `CreditWallet` хранит текущую проекцию баланса;
- `CreditTransaction` является неизменяемым журналом;
- каждая финансовая операция имеет idempotency key;
- новый пользователь получает 10 кредитов;
- одна генерация или доработка стоит 4 кредита;
- техническая ошибка и отмена queued-задачи возвращают ровно списанную сумму;
- повторная обработка одного события не изменяет баланс второй раз.

Были определены пакеты:

| Код        | Кредиты |        Цена |
| ---------- | ------: | ----------: |
| `mini`     |      20 |  25 000 UZS |
| `standard` |      60 |  69 000 UZS |
| `pro`      |     160 | 169 000 UZS |

Платёжная архитектура отделена от провайдера через `CheckoutProvider`. Реализован только `MockPaymentProvider`; он разрешён исключительно при `NODE_ENV != production` и `AI_PROVIDER=fake`. Production-покупки остаются отключёнными до интеграции Payme или Click.

## 10. 31 июля — 1 августа: новая административная модель

Последний крупный этап существенно изменил первоначальную административную архитектуру:

- добавлен отдельный Vite/React/Mantine workspace `admin`;
- добавлен общий пакет контрактов `packages/admin-contracts`;
- профиль получил nullable email и уникальный телефон;
- добавлен seed-скрипт администратора Supabase Auth по номеру `+998` и паролю;
- backend разрешает CORS для настроенного `ADMIN_ORIGIN`;
- локальная desktop-админка может использовать `AdminPhone` только вне production;
- production API требует проверенный Supabase Bearer token или cookie session и роль `ADMIN`;
- добавлены dashboard, пользователи, генерации, финансы и тарифы;
- добавлены отмена генерации администратором и ручная корректировка кредитов.

Одновременно были удалены неиспользуемые сущности и API:

- `AiModel` и `PlanModel`;
- `Notification`;
- `SystemSetting`;
- `AuditLog`;
- пользовательские и административные endpoints моделей, уведомлений и настроек.

Конфигурация AI теперь находится в серверном коде и окружении. Это делает фактическую реализацию проще исходного ТЗ, но означает, что управление моделями, уведомлениями и глобальными настройками через UI больше не является текущей функцией.

## 11. Текущая архитектура после всех этапов

### 11.1. Приложения

- Основное приложение: Next.js 16, React 19, Tailwind CSS 4, shadcn/ui/Radix.
- Локальная отдельная админка: Vite, React Router, Mantine, TanStack Query.
- Backend: Next.js Route Handlers и серверные feature services.
- Database: PostgreSQL через Prisma.
- Auth/Storage: Supabase.
- Canvas: Fabric.js.
- Image processing: Sharp.
- AI: fake provider или Vertex AI Gemini, выбранный сервером.

### 11.2. Главные действующие инварианты

- Бизнес-таблицы изменяются только через Prisma.
- Клиент не выбирает внешний AI model ID.
- Входы каждой генерации сохраняются как snapshot.
- Исходное изображение не изменяется генератором.
- Оригинальный AI-результат и пользовательский результат хранятся отдельно.
- Владелец проверяется на каждом пользовательском ресурсе.
- Списания, возвраты и платежные события идемпотентны.
- Mock AI и mock payment имеют явные безопасные ограничения окружения.

## 12. Что было заменено или отменено

| Раннее решение                          | Текущее решение                                                |
| --------------------------------------- | -------------------------------------------------------------- |
| Пользователь выбирает AI-модель         | Модель выбирается сервером из окружения                        |
| Таблицы `AiModel` и `PlanModel`         | Статическая server-side model configuration                    |
| Уведомления и глобальные настройки в БД | Удалены из текущего объёма продукта                            |
| Обязательный `AuditLog`                 | Таблица удалена; отдельный аудит требует нового решения        |
| Несколько страниц процесса создания     | Единый `/app/[id]` workspace                                   |
| Форма доработки внутри результата       | Универсальный плавающий composer                               |
| Только дневной лимит                    | Дневной лимит плюс транзакционный кредитный баланс             |
| Самописные UI primitives                | shadcn/ui/Radix с Renoa-расширениями                           |
| Единая Next.js-админка                  | Next.js overview плюс отдельная локальная Vite/Mantine-админка |

## 13. Открытые направления

Следующие возможности не следует считать реализованными:

- production-интеграция Payme или Click;
- production-ready login flow отдельной Vite-админки;
- системные уведомления;
- UI управления AI-моделями;
- глобальные настройки и watermark assets через админку;
- отдельный постоянный audit trail административных изменений;
- подключённые Trigger.dev/Sentry workflows;
- подтверждённая end-to-end проверка всех authenticated canvas-сценариев в production-подобном окружении.

## 15. Правило дальнейшего ведения истории

Новые значимые изменения следует добавлять сюда отдельным датированным разделом. Старые планы остаются архивом принятых решений, но при расхождении приоритет имеют:

1. текущая Prisma-схема и миграции;
2. серверные и клиентские контракты в коде;
3. обновлённое техническое задание;
4. эта история;
5. старые specs/plans и локальные SDD-артефакты.
