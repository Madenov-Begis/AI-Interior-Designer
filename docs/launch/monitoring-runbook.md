# Production monitoring runbook

Дата ввода: 1 сентября 2026 года.

## Что проверяется

GitHub Actions workflow `Production monitoring` запускается каждые 15 минут и вручную через `workflow_dispatch`.

Публичный smoke проверяет:

- `ruvie.cc`, страницу входа и `admin.ruvie.cc`;
- точный redirect `www.ruvie.cc` на основной домен;
- доступность packages API и сохранение `paymentMode=disabled`;
- ожидаемый `401` защищенных user/admin API без сессии.

Проверка production-базы выводит только агрегированные счетчики и падает при любом из условий:

- больше 3 `FAILED` генераций за 30 минут;
- хотя бы одна `QUEUED` старше 15 минут;
- хотя бы одна `PROCESSING` старше 30 минут;
- больше 3 `TECHNICAL_REFUND` за 60 минут.

Пороги можно временно переопределить переменными workflow `FAILED_WINDOW_MINUTES`, `MAX_RECENT_FAILED`, `QUEUED_STALE_MINUTES`, `PROCESSING_STALE_MINUTES`, `REFUND_WINDOW_MINUTES` и `MAX_RECENT_TECHNICAL_REFUNDS`. Изменение порогов требует отдельного коммита с объяснением причины.

## Сигнал и восстановление

При ошибке workflow открывает GitHub issue `[monitoring] Production health check failed` или добавляет в уже открытый issue ссылку на новый run. После успешного run issue закрывается автоматически. Доступ к подробным Actions logs должен оставаться только у участников репозитория.

Порядок реакции:

1. Открыть ссылку на упавший Actions run и определить, не является ли ошибка кратким сетевым сбоем.
2. Для недоступного домена проверить Vercel deployment, domains и runtime logs.
3. Для `FAILED` проверить error code и provider/runtime logs, не копируя prompt или приватные URL в issue.
4. Для зависших задач проверить Vertex request и reservation expiry. Не менять статус и баланс вручную до сверки `UsageEvent` и `CreditTransaction`.
5. Для technical refund проверить соответствующие failure-события и отсутствие повторного refund.
6. После исправления запустить workflow вручную и убедиться, что incident issue закрыт успешной проверкой.

## Ограничения

Это базовый uptime/operations контроль для закрытой beta. Он не заменяет frontend/backend exception tracking, Google Cloud budget alert и отдельный paging-канал. Sentry подключён в коде frontend/backend/admin; перед расширением аудитории необходимо задать DSN и проверить доставку событий и alert rules.

## Автоматическое восстановление резервов

Добавлен workflow `Recover expired generation reservations`: каждые пять минут
он обрабатывает `RESERVED` с истёкшим `expiresAt`, только для `QUEUED` и
`PROCESSING`. Используется существующий секрет `SUPABASE_DATABASE_URL` и TLS
с проверкой сертификата. Расписание начнёт работать после публикации workflow
в default branch; локальное изменение файлов его не активирует. GitHub может
задерживать scheduled runs, поэтому пять минут — интервал запуска, не SLA.

Восстановление переводит задачу в `FAILED` и возвращает сохранённую сумму
резерва в одной транзакции. Повторный запуск не начисляет кредиты повторно.
Готовые и отменённые задачи не меняются; AI-запросы автоматически не повторяются.
Одна ошибка не останавливает обработку остальных записей. Неудачный возврат
оставляет резерв для следующего запуска и завершает workflow с ошибкой.

Команды требуют явно заданного `SUPABASE_DATABASE_URL` (не выводить его в логи):

- `pnpm recover:generations` — только подсчёт кандидатов, без изменений;
- `pnpm recover:generations --apply` — транзакционный возврат;
- `pnpm recover:generations --help` — справка без подключения к базе.

Один запуск ограничен 2000 резервами. В логах только агрегированные счётчики;
при `failed > 0` проверить доступность PostgreSQL и следующий run. При backlog
повторить запуск; существующий generation-health monitoring остаётся включён.

Worker сначала фиксирует ошибку и возврат, затем очищает частичные файлы.
Если подтверждение успешного COMMIT потерялось, успешный результат сохраняется.
Если статус БД невозможно подтвердить, файлы остаются нетронутыми. Подтверждённые задачи удаления сохраняются в PostgreSQL и повторяются обслуживанием
Storage. Если БД недоступна до записи задачи, требуется отдельная сверка файлов;
полный аудит таких потенциальных orphan objects этим механизмом не покрывается.

## Очередь файлов и временные загрузки

`pnpm maintain:storage` показывает число готовых задач без изменения данных.
`pnpm maintain:storage --apply` обрабатывает до 100 файлов за запуск, использует
CAS lease и backoff до 24 часов. Задача удаляется только после подтверждения Storage.
Повторное удаление уже отсутствующего объекта безопасно. Workflow запускает
обслуживание после восстановления кредитов, даже если предыдущий шаг завершился ошибкой.
Необходимы `SUPABASE_DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.

Записи временных загрузок очищаются через сутки после истечения срока. Их файлы
попадают в очередь заранее с задержкой 2 часа 15 минут: подписанное разрешение
загрузки успевает истечь и не сможет создать объект заново после очистки.
Просроченные rate limit buckets также удаляются обслуживанием.
