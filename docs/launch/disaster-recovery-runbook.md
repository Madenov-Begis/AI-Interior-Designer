# Disaster recovery runbook

Дата утверждения для закрытой beta: 1 сентября 2026 года.

## Цели и ответственность

- **RPO beta:** не более 30 часов. Основной ориентир — последние сутки; запас учитывает наблюдавшиеся задержки запуска scheduled workflow GitHub Actions.
- **RTO beta:** не более 4 часов с момента объявления инцидента до восстановления основных пользовательских операций.
- **Ответственный:** владелец production-доступов к GitHub, Vercel и Supabase выполняет роль Beta Recovery Owner.
- **Заместитель:** перед расширением beta должен быть назначен второй участник с отдельной учетной записью и MFA.

RPO является целевым пределом потери данных, а RTO — целевым временем восстановления. Они не являются SLA для публичного коммерческого сервиса.

## Что сохраняется

Workflow `Supabase encrypted backup` ежедневно создает один зашифрованный архив с retention 30 дней:

- logical dump схемы `public`;
- data-only dump метаданных `auth` и `storage`;
- все объекты шести приватных Storage buckets;
- manifest Storage с размером и SHA-256 каждого объекта;
- SHA-256 зашифрованного архива.

Секрет шифрования и production credentials находятся в GitHub Actions Secrets и не включаются в artifact или Git.

## Когда объявлять восстановление

Восстановление начинается при подтвержденной потере или повреждении production-данных, ошибочной массовой операции либо недоступности текущего Supabase-проекта, которую нельзя устранить обычным rollback приложения. Ошибка одного запроса или одной генерации сама по себе не требует восстановления всей базы.

## Процедура

1. Зафиксировать время инцидента и назначить Beta Recovery Owner.
2. Остановить новые пользовательские операции. До появления отдельного kill switch используются Vercel rollback/maintenance deployment и ограничение доступа к закрытой beta.
3. Выбрать последний успешный run `Supabase encrypted backup`, завершившийся до повреждающего события.
4. Скачать encrypted artifact и checksum только на доверенную машину. Проверить SHA-256 до расшифрования.
5. Создать отдельный recovery-проект/базу. Не восстанавливать поверх production до проверки результата.
6. Расшифровать архив локально с `BACKUP_ENCRYPTION_PASSWORD`; пароль не передавать в командной строке, логах или issue.
7. Восстановить `public.dump` через `pg_restore` с `--no-owner --no-acl` и остановкой при первой SQL-ошибке.
8. Восстановить необходимые Auth/Storage metadata из `auth-storage.dump` только после сверки версии целевого Supabase и системных схем. При несовместимости создать пользователей поддерживаемым Auth API и восстановить только прикладные связи.
9. Загрузить Storage-объекты в исходные bucket/path без public-доступа. Сверить число объектов, размер и SHA-256 по manifest.
10. Применить все Prisma migrations, появившиеся после выбранной копии, командой `pnpm db:migrate:deploy`.
11. Выполнить проверки: row counts основных таблиц, вход Google OAuth, signed URL приватного объекта, баланс тестового пользователя, чтение workspace и production smoke.
12. Переключить Vercel environment на проверенный recovery stack, выполнить redeploy и повторить monitoring workflow вручную.
13. Возобновить beta-доступ только после успешных проверок. Зафиксировать фактические RPO/RTO и причины расхождений.

## Регулярная проверка

- Каждый день: успешный scheduled backup run, наличие encrypted artifact и round-trip одного временного Storage-объекта.
- Каждый месяц: isolated restore базы и одного Storage-объекта.
- После изменения Prisma, Auth, buckets или backup scripts: внеплановый restore test.
- Перед расширением beta: назначить заместителя, проверить его доступ и провести tabletop recovery без использования production-секретов в переписке.

Последние успешные scheduled runs на момент утверждения: 31 августа и 1 сентября 2026 года. Тестовый database restore и round-trip одного Storage-объекта уже выполнены.
