# Ручное удаление аккаунта в закрытой beta

Статус: рабочая операторская инструкция для закрытой beta; self-service endpoint пока отсутствует. Перед каждым реальным удалением владелец production-доступов отдельно подтверждает пользователя и запуск процедуры. Нельзя удалять пользователя напрямую из `auth.users` до обработки прикладных данных и Storage.

## 1. Регистрация и подтверждение запроса

1. Присвоить обращению внутренний `REQUEST_ID`.
2. Сверить адрес обращения с подтвержденным email аккаунта либо запросить повторное подтверждение через согласованный канал.
3. Зафиксировать user ID внутри закрытой операторской записи. Не помещать email, access token, prompt, signed URL или изображения в GitHub issue.
4. Проверить, не требуется ли временно сохранить конкретные записи из-за спора, fraud review или обязательного требования закона.

## 2. Немедленное прекращение доступа

1. В одной проверяемой административной операции изменить `Profile.status` на `DELETED`, установить `deletedAt` и убрать роль `ADMIN`, если она была назначена. Защита последнего администратора должна отработать до изменения.
2. После смены статуса все API Ruvie отклоняют даже еще не истекший JWT, потому что `requireCurrentUser` требует активный Profile.
3. Отменить допустимые `QUEUED` генерации с обычным cancellation refund. Для `PROCESSING` дождаться terminal state либо применить существующую процедуру failure/refund; не менять баланс отдельной SQL-командой.
4. Убедиться, что в мониторинге нет активной генерации этого пользователя.

Удаление Auth user само по себе не считается отзывом уже выданного JWT: Supabase указывает, что token может оставаться криптографически действительным до expiry. Основной барьер Ruvie — статус Profile; прямой пользовательский доступ к Storage дополнительно закрыт отсутствием public/user policies.

## 3. Инвентаризация перед удалением

Сформировать закрытую ведомость только с техническими ID и количеством объектов:

- проекты, генерации, references и visual prompts;
- `MediaFile` с bucket/path;
- незавершенные usage reservations;
- баланс и `CreditTransaction`;
- payment orders/events;
- Auth identities и Storage objects, владельцем которых является пользователь.

Перед изменением данных должен существовать успешный encrypted backup. Само пользовательское изображение нельзя прикладывать к заявке на удаление.

## 4. Удаление и обезличивание

1. По сохраненному списку удалить физические объекты из приватных Storage buckets и проверить отсутствие каждого bucket/path.
2. Удалить или soft-delete проекты, references, generations, usage и не требуемые для учета MediaFile в порядке внешних ключей.
3. Записи, которые необходимо сохранить по финансовым или юридическим причинам, оставить только в минимальном составе. Profile для их FK переводится в `DELETED` и обезличивается: очищаются email, phone, имя, avatar и другие прямые идентификаторы; технический UUID не используется для повторного контакта.
4. Удалить Auth identities/user поддерживаемым Admin API после удаления принадлежащих пользователю Storage objects. Supabase может отклонить удаление Auth user, пока он является владельцем Storage objects.
5. Не редактировать journal баланса задним числом и не удалять отдельные финансовые строки без утвержденного срока хранения.

Для production следует использовать отдельный проверяемый maintenance script с dry-run и явным подтверждением user ID. Одноразовые SQL-команды в Dashboard не являются утвержденной процедурой.

## 5. Проверка результата

- старый bearer token получает `401` от Ruvie API;
- OAuth-вход не восстанавливает старый Profile и данные без отдельного решения о повторной регистрации;
- signed URL удаленных объектов не выдается, bucket/path отсутствуют;
- поиск по прежнему email/phone не находит активный Profile;
- нет `QUEUED` или `PROCESSING` генераций и незакрытой reservation;
- финансовые записи, если сохранены, не содержат лишних персональных полей;
- monitoring и runtime logs не показывают новых ошибок.

## 6. Ответ пользователю

Отправить подтверждение по шаблону из `support-response-templates.md`: дата завершения, категории удаленных данных, категории и основание временно сохраненных записей, а также указание, что encrypted backups перезаписываются в течение 30 дней.

## Что еще нужно автоматизировать

Перед публичным запуском создать и протестировать maintenance script на отдельном пользователе, добавить idempotency/audit record и провести полный сценарий Auth + Prisma + Storage. До этого процедура остается ручной и требует двойной проверки технических ID.
