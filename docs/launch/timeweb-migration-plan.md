# Перенос Ruvie на Timeweb VPS

## Решение

Проект находится в разработке, поэтому серверная база начинается пустой. Данные
старой Supabase-базы не переносим. Ветка переноса не меняет работающий production,
пока её отдельно не опубликуют.

На VPS запускаются Docker-контейнеры:

- Caddy принимает HTTPS-запросы и направляет их сайту и админке;
- Next.js обслуживает сайт и API;
- отдельный worker выполняет генерации из очереди PostgreSQL;
- PostgreSQL хранит пользователей, проекты, кредиты и задания;
- файлы изображений лежат в приватном Docker volume.

Вход работает напрямую через Google OAuth. Приложение само выдаёт сессии и
сохраняет их в PostgreSQL через Prisma. Новому пользователю профиль создаётся
при первом входе. Совпадение email не даёт доступ к чужому профилю.

Kafka и отдельное объектное хранилище для первого запуска не нужны. Резервные
копии настраиваются средствами сервера Timeweb. Деплой в будущем будет через
GitHub Actions; в эту работу не входит настройка серверного backup или деплоя.

## Что подготовлено в ветке

- Удалены runtime-зависимости от Supabase и Vercel, их старые скрипты и workflow.
- История старой базы заменена тремя миграциями для новой пустой PostgreSQL.
- Сайт, админка и worker собираются в Docker-образы.
- Локальный Compose запускает тестовую PostgreSQL и автоматически применяет
  миграции.
- Пользовательские Docker-команды находятся в `package.json`.
- Production Compose и Caddyfile остаются заготовкой для настройки на VPS.

## Локальная проверка

Нужны запущенный Docker Desktop, Node.js 24 и pnpm.

```bash
pnpm docker:up
pnpm docker:test
pnpm docker:down
```

После `docker:up` сайт доступен по `http://localhost:3000`, админка — по
`http://localhost:8080`. Перед запуском выберите локальный Docker context.
Без OAuth-ключей в `.env.local` локальная проверка использует фиктивные
credentials и не выполняет вход. Если добавить настоящий OAuth Client ID и
Secret и зарегистрировать `http://localhost:3000/auth/callback` в Google Cloud,
можно проверить и вход. Генерации по умолчанию отключены. Проверка запуска
контейнеров, HTTP, worker, миграций и интеграционных сценариев не вызывает
Vertex AI.

Без Docker код проверяется командами `pnpm test`, `pnpm test:ui`,
`pnpm typecheck`, `pnpm lint`, `pnpm prisma:validate`,
`pnpm admin:test` и `pnpm admin:build`.

## Что останется перед переключением

1. Проверить свежую сборку и локальный запуск Docker после очистки ветки.
2. Создать VPS, настроить домены, HTTPS, Google OAuth callback и секреты приложения.
3. Проверить на VPS реальный вход, загрузку/скачивание файлов, генерацию,
   кредиты и админку.
4. Отдельно настроить серверные резервные копии и GitHub Actions для деплоя.
5. Обновить публичные юридические документы и тексты, описывающие обработчиков
   данных и места хранения: сейчас они соответствуют старой production-среде.
6. Лишь после этих проверок переключить домены на VPS.

До последнего шага текущий production продолжает работать на прежней версии.
