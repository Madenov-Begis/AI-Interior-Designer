# Работа с Codex в проекте Ruvie

## 1. Что загружается автоматически

Codex автоматически получает инструкции из корневого `AGENTS.md` и более узкого `AGENTS.md` рядом с изменяемыми файлами. Остальная документация читается по маршрутизации из этих инструкций или по прямому указанию в промпте.

Не проси читать весь `docs/` перед каждой задачей. Большой нерелевантный контекст снижает точность и увеличивает вероятность опоры на устаревший отчёт.

## 2. Один чат — один результат

Хорошие границы отдельной задачи:

- одна feature;
- один воспроизводимый баг;
- один рефакторинг с конкретным критерием;
- один аудит;
- один релизный прогон.

Продолжай текущий чат, если уточняешь или исправляешь тот же результат. Создавай новый чат, когда цель независима.

## 3. Структура промпта

Для значимой задачи укажи:

```text
Цель:
Какой наблюдаемый результат нужен.

Контекст:
Страница, маршрут, файлы, ошибка, макет или бизнес-правило.

Ограничения:
Что нельзя менять, какие инварианты сохранить.

Готово, когда:
Проверяемые критерии и необходимые команды.
```

Не нужно задавать роль вроде «ты senior-разработчик». Полезнее описать результат и ограничения.

## 4. Режимы работы

### Диагностика

```text
Найди root cause. Файлы пока не изменяй.
Воспроизведи проблему, укажи доказательства и предложи минимальные варианты исправления.
```

### План сложной задачи

```text
Сначала исследуй текущую реализацию и составь план.
Определи затронутые бизнес-инварианты, API, состояния UI, миграции и тесты.
Не начинай реализацию до завершения анализа.
```

Для этого удобно использовать Plan mode.

### Автономная реализация

```text
Реализуй задачу полностью в рамках текущей архитектуры.
Обнови тесты и документацию, проверь diff и запусти релевантные проверки.
Не делай commit, push и deploy без отдельного запроса.
```

### Code review

```text
Проведи review текущего diff.
Ищи регрессии, security/ownership ошибки, нарушения идемпотентности,
несогласованную frontend/backend validation и отсутствующие тесты.
Не меняй код, пока я отдельно не попрошу исправить замечания.
```

## 5. Пример feature-промпта

```text
Используй $ruvie-fullstack-feature.

Цель:
Добавь переименование проекта из каталога и workspace.

Контекст:
Название хранится в Project.name. Каталог находится в /app/projects.
Используй существующий API-клиент и UI-компоненты.

Ограничения:
Не меняй генерации и source. Максимум 120 символов.
Пользователь может изменять только собственный проект.
Не вводи новый state manager.

Готово, когда:
Название редактируется в обоих местах и обновляется без reload.
Есть loading/error states, backend validation и тесты.
Запусти релевантные тесты, typecheck и lint.
```

## 6. Пример bug-промпта

```text
Используй $ruvie-bug-investigation.

После потери ответа root generation иногда визуально списывает кредиты дважды.
Сначала воспроизведи и найди root cause. Проверь idempotency key,
query cache и reconciliation. Исправь только подтверждённую причину,
добавь regression test и запусти связанные проверки.
```

## 7. Пример UI-промпта

```text
Обнови mobile inspector workspace по приложенному макету.
Используй существующую дизайн-систему и shadcn-компоненты.
Не меняй desktop layout и бизнес-логику генерации.

Проверь 375, 768 и 1440 px, keyboard focus, Escape,
touch targets и horizontal overflow. Покажи результат в браузере.
```

При работе от Figma явно укажи соответствующий Figma skill. При создании заметно нового визуального направления используй frontend/product-design skill, а не только текстовое описание.

## 8. Ожидаемый цикл Codex

1. Прочитать применимые `AGENTS.md`.
2. Проверить состояние Git.
3. Найти минимальный набор кода, тестов и документации.
4. При необходимости уточнить критическое неизвестное или составить план.
5. Реализовать изменение по существующим границам.
6. Добавить/обновить тесты и документацию.
7. Запустить проверки пропорционально риску.
8. Просмотреть diff.
9. Сообщить результат и честный статус проверки.

## 9. Когда применять skills

- `$ruvie-fullstack-feature` — функция проходит через несколько слоёв.
- `$ruvie-bug-investigation` — симптом есть, причина не доказана.
- `$ruvie-release-check` — нужна оценка готовности к публикации.
- `$vercel:nextjs` — сложные вопросы App Router и Next.js.
- `$vercel:react-best-practices` — проверка изменённых React-компонентов.
- `$shadcn` — добавление или изменение shadcn-компонентов.
- `$supabase:supabase` — любая задача с Supabase.
- `$supabase:supabase-postgres-best-practices` — schema/query/index/performance.
- `$vercel:verification` — полный пользовательский сценарий.

Skill не расширяет права на production, deploy, внешние сообщения или destructive actions.

## 10. Когда нужны plugins и MCP

Подключай внешний инструмент только при реальной потребности:

- Vercel — deployments, logs и environment;
- Supabase — проект, Auth, Storage и database operations;
- Figma — актуальный дизайн-контекст;
- GitHub — PR, CI и review;
- Google Drive — внешняя спецификация;
- Codex Security — отдельный security audit.

Если все данные находятся в репозитории, дополнительный plugin обычно не нужен.
