# Инструкции для Codex в проекте Ruvie

## Назначение

Ruvie — fullstack-приложение на Next.js для AI-визуализации интерьера. Эти инструкции действуют для всего репозитория. Более близкий `AGENTS.md` внутри каталога уточняет правила своей зоны.

## Язык

- Общайся с пользователем на русском, если он явно не выбрал другой язык.
- Все новые и изменяемые проектные документы Markdown пиши на русском.
- Комментарии, описания тестов и пользовательские тексты пиши на русском, если это не противоречит API, стандарту или принятому стилю соседнего кода.
- Имена файлов, идентификаторы, команды, названия библиотек, HTTP-методы и общеупотребимые технические термины можно оставлять на английском.
- Не переводи сторонние skills в `.agents/skills`, зависимости и сгенерированные файлы. Их исходный язык является частью внешнего пакета.

## Источники истины

- Карта страниц, пользовательские сценарии и бизнес-правила: `docs/full-product-documentation.md`.
- Архитектурные границы: `docs/architecture.md`.
- Дизайн-система: `docs/design/design-system.md`.
- Стратегия проверок: `docs/testing.md`.
- Схема данных: `prisma/schema.prisma` и применённые миграции.
- Команды и локальный запуск: `README.md` и `package.json`.
- Навигация по документации: `docs/README.md`.

Не читай всю документацию перед каждой мелкой задачей. Сначала классифицируй изменение и прочитай только относящиеся к нему источники. Перед изменением пользовательского флоу, бизнес-правила, API-контракта, схемы данных, кредитов, платежей, генераций, авторизации или административных операций обязательно прочитай соответствующий раздел полной документации и соседние тесты.

Если код и документация расходятся:

1. Зафиксируй конкретное расхождение.
2. Определи, что является фактическим production-поведением.
3. Не меняй бизнес-правило молча.
4. При реализации согласованного изменения обнови код, тесты и документацию в одном наборе изменений.

## Архитектурные границы

- `src/app` — тонкий слой Next.js: маршруты, layouts и Route Handlers.
- `src/client` — пользовательский frontend.
- `src/server` — backend, бизнес-операции и инфраструктура.
- `admin/src` — отдельный frontend админ-панели.
- Prisma — единственный слой доступа к бизнес-таблицам PostgreSQL.
- Supabase SDK используется для Auth, проверки токенов и приватного Storage.
- Клиентские приложения обращаются к backend только через HTTP API.
- Не импортируй server/admin runtime в клиентский код и React/client runtime в серверные сервисы.
- Сохраняй owner-scoped доступ к пользовательским данным.
- Не раскрывай secrets, provider credentials, скрытые server prompts и подписанные URL.

## Обязательный рабочий процесс

Перед изменением:

1. Проверь `git status` и сохрани все несвязанные пользовательские изменения.
2. Найди ближайшие реализацию, типы, тесты и документацию.
3. Сформулируй изменяемый инвариант и критерии готовности.
4. Для неоднозначной или многошаговой задачи сначала составь короткий план.

Во время реализации:

- следуй существующей архитектуре и именованию;
- переиспользуй компоненты, API-клиенты, schemas и сервисы;
- не создавай параллельную дизайн-систему или второй data-access слой;
- обрабатывай loading, empty, error, retry, disabled и success состояния;
- поддерживай согласованную валидацию на frontend и backend;
- сохраняй идемпотентность финансовых и generation-операций;
- добавляй или обновляй тесты для изменённого поведения;
- не делай commit, push, deploy и не изменяй production-данные без прямого запроса пользователя.

После реализации:

1. Просмотри итоговый diff.
2. Запусти минимально достаточные проверки из `docs/testing.md`.
3. Для пользовательского UI проверь затронутый сценарий в браузере, если среда доступна.
4. В финальном ответе перечисли результат, изменённые зоны, выполненные проверки и оставшиеся риски.

## Бизнес-инварианты

Нельзя:

- допускать отрицательный кредитный баланс;
- проводить одно финансовое движение повторно;
- изменять неизменяемый snapshot существующей генерации или заказа;
- возвращать terminal generation/payment в активное состояние;
- выдавать пользователю чужой проект или media;
- принимать доверие к ownership, роли, статусу или сумме только из клиентских данных;
- запускать mock payments или `AdminPhone` в production;
- сохранять секреты в клиентском коде, Git или Markdown-документации.

## Команды

Используй `pnpm`.

Быстрые проверки:

```bash
pnpm test
pnpm test:ui
pnpm typecheck
pnpm lint
```

Админ-панель:

```bash
pnpm admin:test
pnpm admin:server:test
pnpm admin:typecheck
pnpm admin:build
```

Полная проверка:

```bash
pnpm release:check
```

Не запускай полную проверку автоматически после однострочного изменения документации. Выбирай объём проверки пропорционально риску.

## Skills проекта

- `$ruvie-fullstack-feature` — новая или изменяемая fullstack-функция.
- `$ruvie-bug-investigation` — воспроизведение, диагностика и исправление дефекта.
- `$ruvie-release-check` — подготовка релиза и проверка готовности.

Skills дополняют эти инструкции, но не расширяют разрешения и не заменяют продуктовую документацию.
